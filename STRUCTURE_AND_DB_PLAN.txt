4. DATABASE RELATIONSHIP MAP (CORE)
--------------------------------------------------------------------------------

Plain English chain:

  users
    │  (salesperson / created_by / approver)
    │
    ▼
  prospects  (REO-LEAD-xxxx)
    │
    ├──► prospect_stage_history   (every stage change)
    ├──► followups                (calls / meetings)
    │
    └──► onboarding  (REO-ONB-xxxx)   [only after Commercial Approved]
           │
           ├──► onboarding_documents
           ├──► onboarding_approvals  (Finance / Ops / Commercial / Admin)
           │
           └──► customers  (REO-CUS-xxxx)  [only after FINAL approval]
                  │
                  └──► (same docs / history referenced; no re-create of company)

Support tables:
  id_sequences   → safe auto IDs (LEAD / ONB / CUS)
  audit_logs     → who changed what
  notifications  → alerts to users

ASCII diagram:

  ┌─────────┐
  │  users  │
  └────┬────┘
       │ salesperson_id / created_by / updated_by / approver_id
       ▼
  ┌────────────┐     1:N      ┌────────────────────────┐
  │ prospects  │─────────────►│ prospect_stage_history │
  └─────┬──────┘              └────────────────────────┘
        │
        │ 1:N
        ▼
  ┌────────────┐
  │ followups  │
  └────────────┘
        │
        │ prospect 1 : onboarding 0..1
        ▼
  ┌────────────┐     1:N      ┌──────────────────────┐
  │ onboarding │─────────────►│ onboarding_documents │
  └─────┬──────┘              └──────────────────────┘
        │
        │ 1:N
        ▼
  ┌──────────────────────┐
  │ onboarding_approvals │
  └──────────┬───────────┘
             │ after final Approved
             ▼
        ┌───────────┐
        │ customers │
        └───────────┘

Relationship rules (IMPORTANT):
  1. One Prospect → many Follow-ups
  2. One Prospect → many Stage History rows
  3. One Prospect → at most ONE active Onboarding
  4. One Onboarding → many Documents
  5. One Onboarding → many Approval rows (by department)
  6. One Onboarding → at most ONE Customer (after final approval)
  7. Existing customers (direct add) may have NO prospect/onboarding link
     (source = Existing Customer)

6. HOW DATA MOVES (NO RE-ENTRY)
--------------------------------------------------------------------------------

STEP A – Create Prospect
  User fills company + contact + service…
  System saves prospects + generates REO-LEAD-xxxx
  System writes first stage history: → New Prospect

STEP B – Pipeline + Follow-ups
  User changes stage → prospect_stage_history row
  User adds follow-up → followups row (+ update next_followup_date)

STEP C – Commercial Approved
  Stage = Commercial Approved
  UI shows button: Initiate Customer Onboarding

STEP D – Initiate Onboarding
  INSERT onboarding
  COPY from prospect: name, contact, mobile, email, business_type,
       service, temperature, etc.
  User adds only EXTRA: addresses, GSTIN, PAN, vehicle, route, docs
  Create approval rows: Finance, Operations, Commercial, Admin = Pending
  Prospect stage → Onboarding

STEP E – Approvals
  Each department updates onboarding_approvals
  If Rejected → overall_status Rejected → user corrects → resubmit
  If all Approved + Admin Approved → go to code generation

STEP F – Customer Code + Customer Master
  Lock id_sequences (customer) → next REO-CUS-xxxx
  INSERT customers (copy from onboarding; source = New Onboarding)
  Prospect stage → Customer Activated
  Never create a second manual customer for same onboarding

STEP G – Direct Existing Customer (alternate path)
  Admin/authorised user adds to customers with source = Existing Customer
  prospect_pk / onboarding_pk = NULL
  Keep old code if known, else generate new
  Duplicate warning on GSTIN + name

7. ID GENERATION (SAFE)
--------------------------------------------------------------------------------

Table: id_sequences

  prospect   → REO-LEAD-0001
  onboarding → REO-ONB-0001
  customer   → REO-CUS-0001

Rules:
  - Use DB transaction + row lock when generating next number
  - User cannot edit these IDs
  - Customer code only after final Admin approval
